## Phase 1：P0 死锁 / 功能完全失效（5 个）

### 1.1 🔴 resetSendingLock 从未接线 → 切会话/新建时永久死锁

**位置**：App.tsx:448 传 `resetSendingLock: undefined`
**根因**：注释写 "will be wired after usePromptActions"，但 usePromptActions 在 useSessionActions 之后调用，形成循环依赖，从未接上
**后果**：流式中切会话/新建 → isSendingRef 恒 true → 新消息全进队列永不发 → 永久死锁
**修复**：
- App.tsx 建 `resetSendingLockRef = useRef<(() => void) | null>(null)`
- 给 useSessionActions 传稳定回调 `() => resetSendingLockRef.current?.()`
- usePromptActions 返回后 `resetSendingLockRef.current = resetSendingLock`
- 同 drainQueueRef 模式（App.tsx:547 已有先例）
**验证**：流式中切会话 → 新会话立即可发消息；流式中新建会话 → 输入框可用

### 1.2 🔴 session.info 当 RPC 调但无映射 → pending 交互恢复全死

**位置**：App.tsx:364 / App.tsx:408 `call('session.info', { session_id })`
**根因**：bridge.ts COMMAND_TO_WS_METHOD 无 `session.info` key；后端无此 RPC arm（session.info 是纯推送事件）
**后果**：切 session/profile 时 pending 审批/澄清/sudo/secret 弹窗重建永远不执行
**修复**：
- 删除 App.tsx 这两个 RPC 调用块
- 依赖后端推送的 session.info 事件重建弹窗（useSSE.ts:404 / useMessageStream.ts:585 / useGridChat.ts:530 已有消费）
- 若确需按需拉取，须后端先加 RPC arm（独立任务）
**验证**：有 pending 审批时切换 profile → 审批弹窗正确重建

### 1.3 🔴 审批重建 run_id 用 pattern_key → 重建的审批永远无法 resolve

**位置**：ws-event-processor.ts:141 `run_id: (pp.approval.request_id) || fallbackRunId`
**根因**：后端 pending_prompts.approval.request_id 放的是 pattern_key（如 "execute_code"），不是 session_id；extractPendingInteractions 优先取了 pattern_key
**后果**：重建审批 → ApprovalCard 发 approval.respond { session_id: "execute_code" } → 后端 resolve 0 条 → Agent 永久卡死，界面却显示"已批准"
**修复**：
- extractPendingInteractions 的 approval 分支改为 `run_id: fallbackRunId || pp.approval.request_id`（session_id 优先）
- 调用方一律传 session_id 作为 fallbackRunId
- App.tsx:367/411 两处手动映射删除，改用 extractPendingInteractions（与 1.2 合并修）
- ApprovalCard 检查 resolved===0 时提示失败而非假装成功
**验证**：刷新页面 → pending 审批重建 → 点批准 → Agent 继续执行

### 1.4 🔴 宫格丢弃带 session_id 的全局事件

**位置**：useGridChat.ts:338-342 `profileFromSessionId(sessionId)` 守卫
**根因**：假设"全局事件 == 无 session_id"，但后端 build_ws_event 给几乎所有事件注入 session_id
**后果**：terminal.read.request 被丢 → 前端永不回 respond → 后端工具阻塞到超时；notification.show/clear 也丢
**修复**：
- per-agent switch 的 default 分支兜底调 `handleGlobalEvent(eventName, payload)`
- 或显式把 notification.* / terminal.read.request / browser.progress 加入 switch 并委托 handleGlobalEvent
- 不再用"有无 session_id"区分全局/局部
**验证**：宫格模式下 Agent 调 read_terminal → 前端正确回 respond → 工具不阻塞

### 1.5 🔴 terminal.read.request 字段名错

**位置**：useSSE.ts:355 + global-events.ts:59 读 `chunk.start`，后端发 `start_line`
**后果**：终端分页翻页完全失效
**修复**：两处改 `chunk.start_line` / `payload.start_line`
**验证**：终端工具请求读取指定行 → 前端传正确 start_line

## Phase 2：P1 逻辑 BUG（8 个）

### 2.1 宫格 sendTo 锁在 await 后 → 双击双提交

**位置**：useGridChat.ts:204-213
**修复**：`sendingRef.current[profile] = true` 移到连接保障 await 之前（catch 里已有释放）

### 2.2 宫格 error 不 drain 队列

**位置**：useGridChat.ts:445-447
**修复**：error handler 释放锁后，照 message.complete（373-377）那样 drain 下一条

### 2.3 abort 语义不一致

**位置**：useSSE.ts:676（drain）vs useGridChat.ts:243（drop）
**修复**：统一为"abort 停当前 turn，续发队列"（单视图行为）；宫格 abortAgent 改为 drain 而非 clear

### 2.4 handleDeleteSession 不清 wsClient.sessionId

**位置**：useSessionActions.ts:81-86
**修复**：删当前会话时补 `resetSendingLock + resetStream + getWsClient().switchSession('') + 清 profile_session_map[currentProfile]`

### 2.5 宫格 loadMore 立即 evict

**位置**：useGridChat.ts:159-164 `merged.slice(-WINDOW_MAX)`
**修复**：上翻加载不做尾部裁剪；改为锚定滚动位置的头部窗口（对新进消息才 head-evict）

### 2.6 排队消息重复上屏

**位置**：usePromptActions.ts:184+79 / useGridChat sendTo 排队+drain
**修复**：只在排队时上屏，drain 不再追加用户消息（两视图同步改）

### 2.7 单视图 secret 重建 request_id undefined

**位置**：App.tsx:370/414 原样透传 pp.secret_capture（只有 secret_id 无 request_id）
**修复**：与 1.2/1.3 合并——App.tsx 重建统一走 extractPendingInteractions（它做了 secret_id→request_id 映射）

### 2.8 adaptParams 丢弃 execute_command 参数

**位置**：bridge.ts:193 硬编码 `{ name: args.command, arg: '', session_id: '' }`
**修复**：`return { name: args.command, arg: args.args || '', session_id: args.session_id || '' }`
