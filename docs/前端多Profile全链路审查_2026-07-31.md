## 二、P0（功能 BUG / 数据丢失 / 串台）

### P0-1 storage.init() 冷启动必然空载 → 启动恢复链整条失效

**文件**：src/utils/storage.ts:29-64 + src/App.tsx:617,647

**实证链路**：
1. App.tsx:617 mount effect 即调 `storage.init()`
2. init() 经 `call('get_app_data')` → bridge.call → ws-client.sendRpc
3. 此时 WS state='disconnected'（WS 连接在 portReady effect 才发起，App.tsx:660+）
4. ws-client.ts:397 对 disconnected **立即 reject 不排队**
5. storage.ts:54 catch 把 reject 当"首次启动无数据"吞掉 → `_initialized=true` 封死重试

**连锁后果**：
- startupRestored effect 读 `storage.load('profile_session_map', {})` → `{}` → 启动永不恢复上次会话
- msg_cache / titles / theme 跨重启"丢失"（盘上有数据，内存读不到）
- usePromptActions.ts:74 的 `if (!storage.isReady()) await storage.init()` 守卫形同虚设（isReady() 已 true）

**为何开发期不暴露**：HMR 热重载时 wsClient 单例已 connected，remount 后 init 能加载成功。**生产冷启动必现**。

**修复方向**：
- 方案 A：init() 加载前先 `await getWsClient().ensureConnected(timeout)`
- 方案 B：加载失败时不置 `_initialized=true`，保留 `_initPromise=null` 允许重试
- 方案 C：将 storage.init() 调用点移到 WS onOpen 回调之后，startupRestored effect 增加 `storage.isReady()` 门控

### P0-2 ClarifyCard adaptParams 丢弃 profile → 宫格澄清回答盖错章（串台）

**文件**：src/utils/bridge.ts:188-190

**实证链路**：
1. ClarifyCard.tsx:40 传 `profile` → api.ts:303 `call('submit_clarify_response', {clarify_id, response, profile})`
2. bridge.ts:188 `case 'submit_clarify_response': return { request_id: args.clarify_id, answer: args.response }` — **profile 被剥**
3. ws-client.ts:373 见 `params.profile === undefined` → 盖 `activeProfile`（焦点 Agent，非卡片归属 Agent）

**加重因素**：React 冒泡顺序——chip 按钮 onClick 先于卡片 div 的 onFocusChange 执行，直接点非焦点卡片的选项时 activeProfile 还是旧值。

**其余 3 卡干净**：Approval/SlashConfirm 直传 sendRpc params.profile（AgentChatCard.tsx:266/318）；Credential 经 call args 走 adapt default 分支保留 profile。**唯 clarify 一条断链**。

**修复**：adaptParams 该 case 补 profile 透传：
```typescript
case 'submit_clarify_response':
  return { request_id: args.clarify_id, answer: args.response, ...(args.profile ? { profile: args.profile } : {}) };
```

### P0-3 宫格内切会话不重置旧流 → 旧会话终稿注入新会话（跨会话串台）

**文件**：src/components/GridModeView.tsx:272-278 + src/hooks/useGridChat.ts:136-150

**实证链路**：
1. switchToSession（GridModeView.tsx:272）只调 `loadLatest(profile, sessionId)` + `onFocusChange(profile)`
2. loadLatest（useGridChat.ts:136）只 patch sessionId + messages
3. **不重置** accRef[profile]（累加器）、sendingRef[profile]（发送锁）、queueRef[profile]（排队）
4. WS handler 路由只按事件帧 session_id 解析 profile（useGridChat.ts:371），不比 slot 当前 sessionId
5. 旧会话的 message.complete finalize 后 append 进**新会话**的 messages

**复现**：Agent B 流式中 → 侧栏点 B 的另一个历史会话 → 旧流结束后其终稿气泡出现在新会话卡片里。

**修复**：loadLatest / switchToSession 入口先：
- `abortAgent(profile)`（触发后端终止 + 清锁）
- `resetAccumulator(accRef[profile])`
- `sendingRef[profile] = false`
- 清 queueRef[profile]
- patch status:'idle'

### P0-4 单视图 session.info(running=false) 自愈不释放发送锁 → 后续消息静默进死队列

**文件**：src/hooks/useMessageStream.ts:572-590

**实证链路**：
1. 自愈分支做了 flush + completeAssistantMessage + storeSetIsStreaming(false)
2. **不调 drainQueueRef**（对比 onDone :624 有调）
3. isSendingRef 恒 true → 用户下条消息走 handleSend 排队分支（上屏但永不发送）
4. drainQueue 只有 onDone/onError 触发 → 静默丢失，直到切会话/切 Agent 才恢复

**触发场景**：WS 重连致 message.complete 丢失 → session.info 自愈 → UI 恢复可输入但发送锁未释。

**对比**：宫格等价自愈有释锁+drain（useGridChat.ts:574-577），单视图缺失。

**修复**：自愈分支末尾补 `drainQueueRef.current?.()`。

### P0-5 KanbanPanel SSE + 附件下载绕过 /p/ 前缀 → 多 Profile Kanban 失效

**文件**：src/components/KanbanPanel.tsx:1442 + :1105

**实证**：
- :1442 `new EventSource(\`${baseUrl}/api/kanban/events?since=...\`)` 直接用 getApiBase()，无 /p/
- :1105 `window.open(\`${base}/api/kanban/attachments/${a.id}?board=default\`)` 直接用 getApiBase()，无 /p/
- kanbanHttpFallback（bridge.ts:306-318）的 /p/ 注入覆盖不到这两条路径（EventSource 是浏览器原生 API，window.open 绕过 bridge）

**后果**：非 default profile 的 Kanban 实时事件全部丢失 + 附件下载 404 或返回错误数据。

**修复**：
- SSE：connectSSE() 中读 `getWsActiveProfile()`，拼入 `/p/${profile}` 前缀
- 附件：改走 `call('download_kanban_attachment', { attachment_id })` 获取 blob 后触发下载，或手动拼 /p/

## 三、P1（逻辑缺陷 / 不一致）

### P1-1 删除当前活跃 Agent 后 currentProfile 悬空

**文件**：src/components/ProfilePanel.tsx:212-227

handleDelete 成功后只 `cancelDelete()+load()`，从不回调 `onProfileChange`。若删的正是当前选中 Agent：
- App.currentProfile 与 ws-client 盖章变量继续指向已删 profile
- 后续所有 RPC 盖死 profile 名 → 后端解析失败/回退 default（隐蔽串台）
- profile_session_map[已删] 僵尸指针无人清理

**修复**：删除成功后 `if (deletingTarget === currentProfile) onProfileChange?.('default')`，并同步删除 map 中该 profile 条目。

### P1-2 restoreProfileSession 缺 sessionIdMatchesProfile 校验

**文件**：src/App.tsx:421-440 + src/components/GridModeView.tsx:261-268

restoreProfileSession 读 map[profile] 后不经 sessionIdMatchesProfile 校验直接 loadSessionIntoView——与 startupRestored（App.tsx:344）和 handleProfileChange Step 1b（App.tsx:387-389）的校验标准不一致。上游 GridModeView.persistPointers 写 map 同样不校验。

**修复**：restoreProfileSession 加 `sessionIdMatchesProfile(targetId, profile)`；persistPointers 写入前逐条校验。

### P1-3 pending 交互卡片跨 profile/session 泄漏

**文件**：src/App.tsx:708-756 + src/hooks/useMessageStream.ts:554-561

activeClarify/activeApproval/activeSudo/activeSecret/activeSlashConfirm 只在各自 onDone 里清空。handleProfileChange / restoreProfileSession / loadSessionIntoView / clearSessionView / handleSwitchSession / handleNewSession **均不清卡**。

场景：A 有 pending 审批 → 切到 B → 审批卡留在 B 视图；用户点批准 → 响应事件被 currentSessionIdRef 过滤丢弃，A 的 run 后端继续但前端零反馈。

**修复**：在 resetStream 或 loadSessionIntoView/clearSessionView 入口统一清空全部 active* 卡；或 onSessionInfo 改为"先清空再按 pending 填充"。

### P1-4 useSessions.remove() 裸调 storage.remove('session_id')

**文件**：src/hooks/useSessions.ts:93-101

违反 session.ts:130 明令的"禁止裸调"契约。当前唯一调用方 handleDeleteSession 自行补偿了 map 清理，但 remove 是公开 handle，任何新调用方都会留僵尸指针。且删当前会话后 sessionId=null 但 freshDraftReady 仍 false。

**修复**：remove() 内改用 `clearSessionPointer(profileFromSessionId(id))` + `setFreshDraftReady(true)`。

### P1-5 getActiveProfile 重试耗尽后永久放弃

**文件**：src/App.tsx:118-132

5 次指数退避（~12s）耗尽 → setProfileResolved(true) 且 currentProfile 锁死 'default'。gatewayHealth.onOnline（App.tsx:227）只复位 connectionStatus，不重拉 active profile。网关慢启动后恢复时，CLI 设定的真实 active ≠ UI 的 default → 盖章错误且无自愈。

**修复**：记录"耗尽降级"标志，onOnline 时若为降级态则重拉 getActiveProfile。

---

### P1-6 宫格 error 事件丢弃已累积内容 + 无用户反馈

**文件**：src/hooks/useGridChat.ts error case（约 L370-380）

error 事件直接 resetAccumulator(acc) 并清空 streamText/streamParts，已累积的部分响应被丢弃，用户只看到流式气泡消失、无任何错误提示。对比单视图 useMessageStream.onError 会保留流式消息并标记 error + 弹 toast。

**修复**：error 时先 finalizeAccumulator(acc) 将已有 parts 写入 messages（带 error 标记），再追加错误系统消息，最后 resetAccumulator。

---

### P1-7 宫格 sendTo ensureConnected 返回值未检查

**文件**：src/hooks/useGridChat.ts sendTo（约 L213-215）

`await ws.ensureConnected(10000)` 后直接进入 sendRpc，不像 useSSE.send 那样检查 `if (!connected)` 提前返回。若超时但 WS 处于 reconnecting，sendRpc 排入 pendingQueue（30 分钟超时），期间 sendingRef=true 锁持有、UI 显示 streaming，用户无感知卡死。

**修复**：检查返回值，false 时释放锁 + patch idle + 追加错误消息。

---

### P1-8 reasoning.end 两视图语义分裂

**文件**：src/hooks/useSSE.ts reasoning.end（约 L175）vs src/hooks/useGridChat.ts reasoning.end（约 L395-400）

宫格在 reasoning.end 时将 acc.reasoning 移入 acc.parts（支持多推理块分离）；单视图仅触发 onReasoningComplete 回调（useMessageStream 中为 no-op），reasoning 留在 acc.reasoning 直到 finalizeAccumulator 一次性推入。多段推理（reasoning→text→reasoning→text）时单视图合并为一块且顺序错乱。

**修复**：将 reasoning.end 的"移入 parts"逻辑下沉到 processAccumulatorEvent，两视图共用。

---

### P1-9 handleCommand 'send' 分支过早释放 isSendingRef

**文件**：src/hooks/usePromptActions.ts:113-122

`try { await send(kickoff) } finally { isSendingRef.current = false }`：send 在 prompt.submit 响应即 resolve，流还在跑 → 锁提前释放 → 下一条 handleSend 直发不排队 → 两轮 turn 共写同一 streamIdRef → parts 交错乱序。

对比：常规 handleSend 持锁到 onDone→drainQueue；宫格 execCommand 'send' 走 sendTo 持锁到 message.complete。

**修复**：删 finally 释锁，对齐常规路径（释锁交给 onDone/drainQueue）。

---

### P1-10 宫格 loadLatest/loadMore 无过期响应守卫

**文件**：src/hooks/useGridChat.ts:136-150 / 153-180

loadLatest 第二个 patch 不校验 `s.sessionId === sessionId`：同 Agent 快速切 X→Y，X 响应晚到 → Y 的 sessionId 配 X 的历史。loadMore 同理。

单视图已全部用同步 ref 守卫（App.tsx:306、useSessionActions.ts:75）；宫格缺等价 per-profile 守卫。

**修复**：patch 前 `if (s.sessionId !== sessionId) return s`。

## 五、确认干净的部分

1. **WS 事件隔离闭环**：routeWsEvent 三分支过滤（current 匹配/pending 缓冲/null 丢弃）完整；pendingSendRef 在 send 成功/失败/超时/flush/resetStream 五条路径均成对 reset；flushPendingBuffer 重放走同一 routeWsEvent 权威处理器
2. **宫格 per-agent 路由正确**：handler 按 profileFromSessionId 精确路由到 per-profile 状态槽；sendTo 的 sessionIdMatchesProfile 校验在 await 前执行；无 session_id 事件走 handleGlobalEvent
3. **盖章一致性**：sendRpc 无条件盖章（activeProfile ?? 'default'）；宫格 sendTo 显式传 profile 不被覆盖；bridge.call HTTP 层 /p/ 前缀对齐；Approval/SlashConfirm/Credential 宫格模式均显式传 profile
4. **累加器单一权威源**：两视图共用 StreamAccumulator + processAccumulatorEvent + finalizeAccumulator；serverContent 兜底逻辑正确
5. **消息渲染单一权威源**：MessageRow 两视图共用（单视图 MessageContainer + 宫格 AgentChatCard），无平行渲染器
6. **slash 结果处理单一权威源**：interpretSlashResult 纯函数，两视图各自执行副作用
7. **ModelContext 消除 prop drilling**：Provider 在 App 层，消费方 ModelPill/InputArea/GridModeView，宫格 per-agent model 覆盖正确（state.modelName ?? context）
8. **类型单一来源**：Session = re-export SessionInfo；ChatMessage/MessageRole 唯一定义在 lib/chat-messages.ts；types/index.ts re-export
